# Story Machine — 把一篇故事變成可匯入的劇本

輸入一份完整的故事（Markdown 或純文字），機器會反覆跑「作者 AI → 程式驗證 → 評審 AI → 作者修改」，直到產出一份通過平台匯入檢查與發佈門檻的 `scenario.json`。

## 為什麼這樣設計

- **驗證器是純程式，不是 AI。** 它直接呼叫平台匯入時用的整理器（`normalizeImported`）、匯入報告（`buildImportReport`）和送審門檻（`checkScenarioQuality`），再加上結局／NPC 情報的引用檢查。兩個 AI 互評容易互相同意；驗證器說不過就是不過，這是迴圈會收斂的原因。
- **格式說明書從程式碼產生。** 作者拿到的 JSON 規則來自 `lib/ai/scenario-json-prompt.ts`，跟 `/scenarios/prompt` 頁面同一份；遊戲格式改了，機器自動跟著改。
- **每個角色都是「stdin 進、stdout 出」的指令。** 作者和評審預設用不同的模型（Claude 寫、Codex 評），但任何 CLI 都能替換。

## 需要什麼

- 本專案裝好依賴（`npm ci`）
- `claude` CLI（Claude Code）與 `codex` CLI，兩個都要登入過。只有一個也行，見下方「只用一個模型」。
  介面頂部會直接顯示這兩個 CLI 目前的狀態，不用自己猜。

三個 LLM 角色，各自可以換模型：**作者**寫劇本、**評審**找必修問題、**試玩**判斷好不好玩。中間的驗證器是純程式，不是模型。

## 介面（推薦）

```bash
npm run story-machine:ui        # http://localhost:4171
```

一個本機網頁，跑的是跟 `run.sh` 同一個迴圈、同一批模組，差別在於它把每一步當成資料顯示，而不是一堆滾動的文字：

- 貼上故事、上傳 **PDF / Word / Markdown / 純文字**，或 **貼一個網址直接從網頁抓**。
  抓網頁會用 Readability 取正文，丟掉導覽列與側欄；網址指向 PDF 或 .docx 時會自動改走檔案解析。
  抓回來的文字會先放進輸入框讓你過目，**不會直接開跑**——網頁內容是不可信的來源，作者應該先看一眼。
  基於安全考量，指向本機或內部網路的網址會被擋掉（每一次轉址都會重新檢查），也只接受 http 與 https。
- 頂部顯示 **CLI 連線狀態**：`claude` 與 `codex` 是否安裝、是否登入。沒登入會直接告訴你該跑哪個指令，不用等跑到一半才失敗。
- **模型用選的**，不用手改指令字串。每個角色各自選供應商與模型，下面即時顯示組出來的指令；選「自訂指令」就回到原本的自由格式。
- 每一輪一張卡片，上面有作者／驗證器／評審三個狀態燈。
- 驗證器報告分成阻斷（紅）、警告（黃）、資訊三區。
- 評審的每一條必修都是一張卡，附規則編號、出問題的位置、以及具體改法。
- 產出的劇本會先以結構呈現（地點與證物、NPC、目標、結局與條件），原始 JSON 收在下面。
- 通過後可直接複製 JSON 或下載 `scenario.json`。
- 右下角的執行紀錄是作者／評審 CLI 的 stderr，一個步驟跑好幾分鐘時，這是唯一看得到進度的地方。
- 迴圈結束後會再跑一輪 **試玩評審**（可關閉）：七項評分、會讓人玩不下去的地方、以及做得好的地方。
- 每一版劇本都附 **劇本地圖**：地點是卡片（開放／已知未開／隱藏），線是路徑、「到過會發現」、解鎖依賴；卡片上列出證物與在場 NPC，區域用虛線框起來。點地點看描述、證物怎麼拿、解鎖條件、可前往哪裡；點 NPC 看個性、目標條件、每條情報的解鎖門檻、觸發事件。從開放地點走不到的房間會直接標出來。
- 故事太長會 **先濃縮**：超過門檻（預設 25,000 字）時，先把故事濃縮到約 12,000 字，只留地點、人物、祕密、物品、結局與因果鏈，模型再從濃縮版設計結構。門檻與目標字數在「模型與進階設定」裡改；濃縮用哪個模型在「濃縮」角色選，預設 sonnet（摘要不需要最強的模型，需要快的）。
  實測模型會超過目標字數：要求 12,000 字，opus 交回 31,000 字。提示詞已改成硬上限加每條目預算，但仍請把目標當「量級」而不是精確值。

另有兩個分頁：

- **只驗證 JSON**：貼一份現成的劇本 JSON，直接看驗證器報告，不呼叫任何 AI。
- **先前的執行**：列出硬碟上所有跑過的結果，點一筆就把當時的畫面整個叫回來——每一輪的產出、驗證器報告、評審意見、試玩評分都在。
  它是從檔案重建事件流，走跟即時執行完全相同的渲染路徑，所以**命令列用 `run.sh` 跑的結果也看得到**（兩者寫出來的檔案格式相同）。

檔案照樣會寫到硬碟（`stories/ui-<id>/`），格式與下面 CLI 的輸出相同。執行狀態本身只存在記憶體，但因為歷史是從檔案讀的，伺服器重啟不會弄丟任何東西。

改連接埠：`PORT=8080 npm run story-machine:ui`。

## 用法（CLI）

```bash
scripts/story-machine/run.sh my-story.md
```

輸出在 `my-story` 同目錄的 `out/`：

| 檔案 | 內容 |
|---|---|
| `roundN.prompt.txt` | 第 N 輪給作者的完整 prompt |
| `roundN.json` | 第 N 輪作者產出的 JSON |
| `roundN.report.txt` / `.json` | 驗證器報告（阻斷／警告／資訊） |
| `roundN.critic.txt` | 評審意見 |
| `scenario.json` | 最後通過（或最後一輪）的版本 |

通過後：打開平台「建立劇本 → 貼上 JSON」，貼入 `scenario.json`，按匯入。匯入報告應該是乾淨的，因為驗證器跑的就是同一套檢查。

### 跑滿輪數仍未通過？接著跑，不要從頭來

介面的結果橫幅上有「再跑 N 輪」：從最後一輪的 JSON、驗證器報告、評審意見接著進入修正迴圈，不重新濃縮、不重寫第一輪，輪次編號繼續往上數（第 3 輪之後接第 4 輪），檔案寫進同一個目錄。命令列跑的結果也能在「先前的執行」裡接續。

介面的輪數上限是 10；歷史重播不限輪數。一般 2 到 3 輪就能看出收不收斂：必修數字沒有往下掉，多跑幾輪也只是同一個模型繞同樣的圈，這時候該換的是素材切法（拆成單一場次）而不是輪數。

### 調整

```bash
MAX_ROUNDS=5 scripts/story-machine/run.sh my-story.md
WRITER_CMD='claude -p --model opus' CRITIC_CMD='claude -p --model sonnet' scripts/story-machine/run.sh my-story.md
```

只用一個模型時，讓評審用不同的 model 或至少是一個乾淨的 session（`claude -p` 每次都是新 session）。效果比跨模型弱一點，但驗證器仍然是硬的。

### 單獨跑某一步

```bash
npm run story-machine -- validate out/round1.json                    # 只看驗證器
npm run story-machine -- writer-prompt my-story.md > p.txt            # 拿 prompt 去別的地方用
npm run story-machine -- extract --story my-story.md < out.txt > s.json  # 抽 JSON 並填回原文
npm run story-machine -- condense-prompt my-story.md 12000 > p.txt    # 濃縮用的 prompt
```

## 試玩評審（好不好玩）

驗證器和評審回答的是「這份劇本跑不跑得動」。試玩評審問的是另一件事：**四個玩家坐下來玩兩小時，會不會覺得好玩。**

它在迴圈結束後跑一次，**不擋關**——好不好玩是品味，品味不該進閘門。評分表在 `fun-rubric.md`，七個項目各 1–5 分：開場鉤子、線索鏈、卡關風險、NPC 深度、選擇的重量、節奏、恐怖感。另外會列出「會讓某一場遊戲真的變難玩」的具體風險，每條都要附改法。

它讀劇本的方式跟玩家一樣：看不到 `full_story`、看不到 `gm_notes`、看不到證物的 `how`。那是唯一能看出死路的視角。

單獨跑：

```bash
npm run story-machine -- fun-prompt my-story.md out/scenario.json > p.txt
codex exec --skip-git-repo-check - < p.txt
```

環境變數 `FUN_CMD` 可指定它用哪個模型，預設跟評審相同。

**這不能取代真人試玩。** 它抓得到結構性的無聊（地點沒東西、線索單線、結局沒差別），抓不到節奏和氣氛實際跑起來的感覺。

## 轉換決定不進主持人的提示詞

平台會把 `gm_notes` 整段塞進主持人每一回合的系統提示詞。作者的【轉換決定】（travel_mode 怎麼選、id 怎麼命名、合併了哪些 NPC）和每輪的【本輪修正】是審稿用的，主持人讀了沒有用，卻佔掉大量篇幅（實測一份戰役劇本 9,258 字的 gm_notes 裡有 7,275 字是這些）。

現在作者把它們寫在頂層欄位 `conversion_notes`；迴圈裡評審照樣看得到（規則 1 的「補載體要列出」靠它），驗證器也不會把它當未知欄位。最終輸出時 `finalize` 把它剝掉存成 `decisions.md`，舊格式藏在 gm_notes 裡的【轉換決定】【本輪修正】段落也一併抽出。`gm_notes` 只留桌邊規則：回合對時間、哪些事件由 GM 在第幾回合結算、NPC 抉擇怎麼判、節奏與伏筆。介面上有「轉換決定與修改紀錄」面板可以看，並顯示主持人實際會讀到幾個字。

```bash
npm run story-machine -- finalize out/round3.json --decisions out/decisions.md > out/scenario.json
```

## 用量（token）

每一步的真實用量會記在執行目錄的 `usage.json`，介面上顯示在該步驟的狀態燈旁邊，結果橫幅有合計，「先前的執行」列表也有。

- Claude：作者／濃縮／試玩預設用 `claude -p --output-format json`，回應裡帶 `usage` 與 `total_cost_usd`。機器會拆開這個信封再抽 JSON，所以 `--output-format text` 照樣能用，只是沒有用量。注意每一次 `claude -p` 呼叫都帶著 Claude Code 自己的系統提示，約兩萬 token 的快取讀取，那是固定開銷。
- Codex：從 stderr 的 `tokens used` 取合計，沒有輸入／輸出的拆分。
- 費用欄位是依 Anthropic 定價算的參考值。用 claude.ai 方案登入時計的是方案額度，不是這個數字。

## 作者不抄原文（full_story 由系統填入）

作者輸出的 JSON 裡 `full_story` 只寫佔位字串 `__FULL_STORY__`，機器在抽出 JSON 之後自己把原文填回去（`extract --story <story.md>`）。評審與修正的提示詞也用佔位取代，不重複塞同一段文字。

這樣改的原因：以前規則要求作者逐字抄原文，一篇六萬八千字的故事就是六萬八千字的輸出，一次 opus 執行跑了 24 分鐘，最後在抄到一半時撞到輸出上限被截斷，整輪作廢。現在輸出大小跟輸入長度無關。

原文不超過平台上限（100,000 字）時，`full_story` 放的是原文；超過時放濃縮版，好過一篇在句子中間被切斷的故事。

## 兩條設計規則（驗證器會抓）

- **起點只有一個。** 引擎把 nodes 裡第一個 `unlocked` 的地點當起點。自由移動模式下其他地點也 `unlocked`，或 edges 模式下有 `unlocked` 地點沒有路徑從起點走到，都算多個起點，驗證器直接阻斷。其他地點用 `discovered` 加 `unlock` 條件（`visit:起點id` 最常見），或 `hidden` 加 `discovers` 帶到。
- **證物與地點的文字只寫所見。** `reveal_text` 是玩家拿到證物那一刻看到的東西，`desc` 是還沒調查就看得到的外觀；兩者都不寫它代表什麼、真相是什麼、NPC 會怎麼反應。驗證器用關鍵字啟發式抓（「證明」「其實」「他會」…）只給警告；抓不到的交給評審規則 9。

## NPC 觸發事件的地點與時機

引擎在 `npc_encounters` 的 `when` 成立的那一回合就觸發，預設「無論隊伍在哪」都出現。以前作者只能這樣寫，結果是玩家在岩洞拿到日誌，鎮長下一回合就出現在岩洞。

引擎現在多了兩個可選欄位：`at`（地點或區域 id：條件成立後，等隊伍到那裡才觸發）與 `delay`（回合數：條件成立後至少等幾回合）。舊劇本沒有這兩個欄位，行為不變。作者提示詞要求反應「拿到某物／完成某事」的事件一律加 `at`；驗證器對沒加的給警告；評審規則 10 負責判斷原文是否真的允許「隨時找上門」。地圖的 NPC 細節會標出每條事件在哪裡、幾回合後觸發。

## 什麼是「通過」

1. 驗證器沒有任何**阻斷**（格式錯、引用不存在、內容被截掉、發佈門檻沒過）
2. 評審沒有任何 **blocking**（見 `rubric.md`：偷加劇情、目標不是事件、目標是複合句、NPC 沒條件、線索沒地點、結局到不了、簡介洩題）

驗證器的**警告**不擋，但會一併餵給評審和作者，通常會被順手修掉。

## 它做不到的事

- 真正判斷好不好玩。試玩評審能抓結構性的無聊，但節奏和氣氛還是要真人玩過才知道。
- 保證故事本身適合這個引擎。如果故事的祕密不附著在「地點 + 動作」上，作者只能硬拆——這時候先用平台上的「我只有一個點子」訪談 prompt 把故事改造，再丟進機器。
- 直接上傳到平台。最後一步是手動貼 JSON（需要登入）。
