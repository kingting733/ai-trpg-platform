# 任務目標怎麼寫（給創作者）

> 一句話版本：**一條目標 = 一件主持人會在故事裡明寫出來的事。** 寫完後問自己：「GM 會寫出哪一句話，讓系統知道這條完成了？」答不出來，就重寫。

---

## 一、系統是怎麼判定的（先懂這個，規則才會有道理）

每一回合，玩家打一句行動，AI 主持人（GM）寫一段敘事。然後有一個**獨立的裁判 AI**只做一件事：

> 讀「玩家這回合做了什麼」和「GM 這回合寫了什麼」，判斷還沒完成的目標裡，有哪些**在這一回合真的發生了**。

裁判的限制決定了一切：

| 裁判做得到 | 裁判做不到 |
|---|---|
| 讀懂 GM 寫的具體事件（「達米恩把鑰匙放在桌上」） | 判斷抽象狀態（「合作關係建立了」） |
| 認出「這件事發生了」 | 猜「玩家心裡決定了什麼」 |
| 記錄多步驟的進度（「已放 2/4 個角落」） | 一次記很多件事、很多分支 |
| 看見骰子成功／失敗在敘事裡的結果 | 知道玩家「打算」做什麼 |

所以：**目標越像一個畫面，判定越穩；越像一個概念，判定越飄。**

所有目標都是**全隊共有**的——任何一位玩家做到，整隊就算做到。沒有「每人各自完成」。

---

## 二、五條規則

### 1. 寫「事件」，不寫「狀態」或「決定」

裁判只看得到 GM 寫出來的畫面。心理狀態、決定、理解、抽象結果，GM 不一定會寫，寫了裁判也不好判。

| ✗ 不要這樣寫 | ✓ 改成這樣 |
|---|---|
| 與達米恩談成合作 | 達米恩親口答應把下一批威士忌交給隊伍運送 |
| 決定保留酒廠生產 | 向工頭下令讓蒸餾器繼續運轉 |
| 理解 1404 室的真相 | 從陳家牌位後方取出那張焚燒到一半的名單 |
| 讓王伯信任你們 | 王伯把 1404 的備用鑰匙交給隊伍 |
| 解決地下室的問題 | 把地下室的封印重新畫好 |

訣竅：句子裡要有**動作 + 對象**，最好還有**東西或地點**。「交出鑰匙」「點頭下令」「把名單拿到手」都是畫面；「合作」「信任」「解決」都不是。

### 2. 一條只放一件事

有先後順序 → 拆成兩條。有「或」 → 改成一件事，把分支放進括號。

| ✗ | ✓ |
|---|---|
| 接管威士忌生意：與達米恩達成合作，或武力控制農場後，明確決定保留酒廠生產並安排下一批威士忌外運 | ① 取得農場的控制權（與達米恩談成合作，或以武力壓制農場）<br>② 向工頭下令維持生產<br>③ 安排好下一批威士忌的外運車隊 |
| 找到帳本並交給警長 | ① 取得帳本<br>② 把帳本交到警長手上 |

拆開之後，每一條完成時玩家都會感覺到進展，結局條件也能分別引用。

### 3. 用劇本裡的正式名字

裁判是拿目標文字去對 GM 的敘事。NPC、證物、地點的名字要跟劇本其他地方**一字不差**。

| ✗ | ✓ |
|---|---|
| 說服那個管理員 | 王伯把備用鑰匙交給隊伍 |
| 找到重要的文件 | 取得「祥安樓倫常慘案」剪報 |

### 4. 多步驟可以，但每一步都要是具體事件

「在四個角落各放一撮米」這種目標**可以用**——裁判會記進度（「已放：東北角、西南角」），全部做完才打勾。條件是每一步都是 GM 會寫出來的動作。

但如果能拆，還是拆：四個角落拆成四條太多，那就改成「把米撒滿神位四周」這種一次性動作；或者用地點條件（「去過四個角落」）取代。

### 5. 能用程式判斷的，不要交給裁判

有些事系統本來就知道，不需要 AI 猜。結局條件和地點解鎖可以直接用這些：

| 你想表達的 | 不要寫成目標，改用 |
|---|---|
| 拿到某件證物 | `item:證物id` |
| 到過某個地點 | `visit:地點id` |
| 某個 NPC 死了／還活著 | `npc_dead:名字` / `npc_alive:名字` |
| 撐到第 N 回合 | `round:N` |
| 蒐集到 N 件某類證物 | `count:標籤:N` |

目標留給**只有 AI 讀得懂的事**：NPC 答應了什麼、儀式做完了、某句話被說出口。

## 三、必要 vs 加分

- **必要**：全部完成才算贏（沒自訂結局時，系統會自動用「所有必要目標完成 → 勝利」）。
- **加分**：不影響勝負，但可以被結局條件引用（例如「必要目標全完成 + 加分目標 A → 真結局」）。

建議：必要目標 2–4 條，超過就想想哪些其實是加分。

---

## 四、不要拿目標做的事

| 這件事 | 該用什麼 |
|---|---|
| 「活著離開」「不要讓 NPC 死」這類**持續狀態** | 結局條件（`npc_alive:`、`visit:出口`） |
| 失敗條件（「聖石被奪走」） | 結局系統裡設一個 failure 結局 |
| 給玩家看的任務說明 | 「簡介」和「開場場景」——目標文字**玩家看不到** |
| 劇情提示（「記得問王伯香灰的事」） | GM 備註 |

---

## 五、自我檢查（寫完每一條都跑一次）

1. 這條目標完成的那一回合，**GM 會寫出哪一句話**？（寫不出來 → 規則 1）
2. 那句話裡只有**一件事**發生嗎？（不只 → 規則 2）
3. 句子裡的人名、物名，劇本其他地方**寫法一樣**嗎？（不一樣 → 規則 3）
4. 這件事系統**本來就知道**嗎（拿到證物、到過地點）？（知道 → 規則 5）
5. 這是「做一次就完」，還是「一直維持」？（維持 → 用結局條件）

## 六、完整範例

以「威士忌農場」為例，玩家要接手生意：

| # | 目標 | 必要 | 完成時 GM 大概會寫 |
|---|---|---|---|
| 1 | 取得農場的控制權（與達米恩談成合作，或以武力壓制農場） | ✓ | 「達米恩伸出手：『成交。』」或「守衛丟下槍，達米恩跪在泥地上。」 |
| 2 | 向工頭老周下令讓蒸餾器維持運轉 | ✓ | 「老周點點頭，拉下閘門，銅管重新嗡嗡作響。」 |
| 3 | 安排好下一批威士忌的外運車隊 | ✓ | 「九指老陳把三輛卡車的鑰匙排在桌上。」 |
| 4 | 從穀倉夾層取得達米恩的帳本 | 加分 | 「你掀開地板，帳本就壓在那裡。」 |

結局：`真結局` 條件 `[["objective:1","objective:2","objective:3","objective:4"]]`；`普通結局` 條件 `[["objective:1","objective:2","objective:3"]]`；`失敗` 條件 `[["round:30"]]`。

## 七、系統會怎麼幫你

- 劇本編輯器的目標欄位旁邊有這份規則的精簡版。
- 用 story machine（`scripts/story-machine/`）產生劇本時，驗證器會對目標文字做檢查：含「決定／理解／知道」、含「或」、太長、看起來是多步驟，都會標出警告；評審會把「目標不是事件」列為必修。
- 遊戲中，每回合的判定結果會寫進伺服器 log（`[objectives:check]`），包含進度備註。如果某條目標「一直不完成」，先看那條 log 再改文字。
