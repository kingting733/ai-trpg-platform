# coc-story — 寫一篇能在這個平台上跑得好的克蘇魯故事

這個平台跟桌上跑團不一樣：主持人是 AI，地圖、證物、NPC 情報、目標、結局全由**伺服器程式**決定，AI 只負責敘述。所以一篇故事「好不好」有兩層意思：

1. **故事本身**——鉤子抓不抓人、線索鏈會不會斷、恐怖有沒有升溫、結局有沒有重量。
2. **引擎吃不吃得下**——每個祕密有沒有「地點＋物件＋動作」、目標是不是 GM 會明寫的事件、NPC 有沒有位置與條件、結局條件程式判不判得出來。

兩層缺一不可。只有第一層，匯入後會被驗證器打回；只有第二層，玩起來像填表。

## 先讀什麼

- **一定讀** `references/engine-constraints.md`——引擎的限制，用寫作者的語言寫。違反它的故事再好也跑不動。
- **一定讀** `references/story-craft.md`——好的 CoC 故事長什麼樣，從十篇故事解剖出來的模式。
- **需要範例時**讀 `references/autopsies/`——每篇故事一張解剖卡（結構、線索網、NPC 表、放進引擎會壞的地方）。想看「鉤子怎麼下」「線索怎麼分三路」就去翻對應的卡。
- **成品長什麼樣**看 `stories/sample.md`（霧港燈塔）：背景／真相／地點／人物／結局五段，這是轉換器最吃得順的形狀。

## 流程

### 1. 弄清楚手上有什麼
使用者可能只有一個點子、一段草稿、一篇完整故事，或一個想改編的現成模組。先問清楚（一次問完，不要拆成好幾輪）：
- 背景時空：1920 年代美國？現代香港／台灣？其他？
- 幾個玩家、預計幾回合（平台上限 40 回合，一回合 = 一位玩家的一個行動；四人團 30 回合每人只有 7–8 個行動，內容要配得上）
- 想要的恐怖類型：鬼屋／邪教／都市傳說／海濱小鎮／探險／密室
- 有沒有一定要保留的元素（角色、場景、結局）

改編現成模組時要特別注意：原文的文字**不能**直接搬進故事（版權），要用自己的話重寫；結構和點子可以學。

### 2. 先設計，再寫文
直接動筆寫散文的故事，十篇有九篇轉不成劇本。先把骨架用表格列出來，逐項對 `engine-constraints.md` 的檢查表核對，確定每個祕密都有地方放、每個目標都是事件、每個結局都判得出來，才開始寫。

骨架至少包含：
- **真相分層**：表面事件 → 人為掩蓋 → 神話真相。每一層都要有自己的證據。
- **地圖**：5–12 個地點，哪些開放、哪些鎖著（鎖的條件）、哪些隱藏（被什麼帶出來）。起點只能一個。
- **線索網**：每個關鍵真相至少三條路拿到（不同地點、不同 NPC、不同動作）。玩家漏掉一條不能卡死。
- **NPC 表**：名字／身分／想要什麼／隱瞞什麼／說了什麼謊／平常在哪／會因為什麼改變／會不會動手。每個 NPC 至少一條情報要有條件。
- **升溫階梯**：恐怖事件按階段排——違和 → 目擊 → 接觸 → 不可理解。平台的理智檢定是靠 GM 敘事裡的關鍵字觸發的（見 constraints），所以每個階段的「畫面」要寫得出來。
- **時鐘**：某個東西在回合數上逼近（第 N 回合會發生什麼）。沒有時間壓力的 CoC 故事玩家會無限嘗試。
- **目標**：2–5 條，每條是一件 GM 會明寫的事件，用劇本裡的正式名字。
- **結局**：2–4 個，每個的條件只用平台支援的那幾種寫法。CoC 的「好結局」通常是「活著離開／封印／付出代價」，不是全贏。

### 3. 寫故事
照 `stories/sample.md` 的五段結構寫。重點：
- **背景**給玩家看得到的處境；**真相**整段是玩家不知道的，寫完整，GM 每回合都靠它理解全貌。
- **地點**每一個都寫：玩家到這裡看得到什麼、可以做什麼拿到什麼（動詞短語）、通往哪裡、什麼時候才進得去。
- **人物**每一位都寫：性格、目的、在什麼條件下會說什麼／做什麼、平常在哪、會不會攻擊。
- **結局**每一個都寫：什麼條件下發生、之後每個人的下場。
- 證物和地點的描述只寫**看到的東西**，不寫它代表什麼——結論留給玩家推，真相放在「真相」段。
- 簡介（給列表用的那一句）不能洩題。

### 4. 自己先審一遍
用 `engine-constraints.md` 最後的檢查表逐條過。特別是這三個 playtest 抓到的坑：
- 目標清單裡有沒有「做了會失敗」的動作（例如「吃東西」）？有就拿掉，失敗條件放結局，不放目標。
- 有沒有兩條目標只差在「地點」（「在東北角上香」vs「在神位上香」）？目標判定器目前**看不到玩家位置**，會混在一起；改用不同的物件或動作區分。
- 關鍵目標是不是第一回合就做得到？勝利要卡在需要檢定或需要先解鎖的證物後面，否則六回合就通關。

### 5. 交出去
- 給 Claude Code session：故事寫進 `stories/<名稱>.md`，接著跑 `scripts/story-machine/run.sh`（或 UI）讓驗證器與評審把關，產出 scenario.json。
- 給一般創作者：把故事貼到平台 `/scenarios/prompt` 頁面的 prompt 後面，AI 會產出可匯入的 JSON；或照 `docs/creator-guide/story-to-scenario-prompt.md` 手動填表。

故事機器的評審標準在 `scripts/story-machine/rubric.md`（必修項）和 `fun-rubric.md`（好不好玩），寫的時候就以通過這兩份為目標，不要等它打回來才改。

## 寫給一般創作者時

同一套內容，但用白話：不講 id、JSON、when 條件，講「這個東西玩家要在哪裡、做什麼才拿得到」。`references/story-craft.md` 刻意寫成可以直接摘給創作者看的語氣；`engine-constraints.md` 的檢查表也是。
